# Architecture

Use-case driven, hexagonal. The domain is pure; everything else plugs into it.

```
src/
  domain/            pure business rules: entities, value objects, domain services
  application/
    use-cases/       one file per use case (commands and queries)
    ports/           interfaces the use cases need (repositories, Clock, UnitOfWork, IdGenerator)
  infra/             port implementations: Postgres (Drizzle), system clock, config
  http/              Elysia routes: validate input, call one use case, map the result
  main.ts            composition root: wires infra into use cases into http
features/            executable spec (Gherkin), tagged with rule ids
tests/               unit and integration tests, step definitions
docs/                spec, glossary, ADRs
```

## Dependency rule

```
http ──▶ application ──▶ domain
infra ─▶ application ──▶ domain
main.ts wires everything
```

| Layer | May import | Must not import |
|---|---|---|
| `domain` | `domain` only | anything else, any npm package |
| `application` | `domain`, `application` | `infra`, `http`, Elysia, Drizzle |
| `infra` | `domain`, `application` (ports) | `http` |
| `http` | `application`, `domain` types | `infra` |

Enforced by `bun run arch` (dependency-cruiser) in the pre-push hook and in CI.

## Domain

- Rules live here, not in use cases.
- Pure functions and immutable values. Same input → same output.
- No `Date`, no `process`, no I/O. Time comes in through the `Clock` port as an argument.
- Business failures are values: return `Result<T, DomainError>`; `throw` only for programmer errors.

## Use cases

- One class per use case with a single `execute(input)` method.
- Commands change state inside one `UnitOfWork` transaction. Queries never change state.
- A use case loads aggregates through ports, asks the domain to decide, persists, returns a `Result`.
- Background jobs are use cases too.

## HTTP

- Routes are thin: validate the body with Elysia schemas, call one use case, map `Result` to a status code.
- No business rule in routes.

## Persistence

- Postgres via Drizzle. `CHECK` constraints mirror invariants where cheap.
- IDs are UUIDv7, generated by the client or the use case.
- Every row has `createdAt` and `updatedAt`.

## Tests

- Scenarios from `features/` run against use cases with in-memory adapters: fast, no database.
- A smaller set runs against the HTTP API with a real Postgres.
- Property tests cover the invariants in the spec.
